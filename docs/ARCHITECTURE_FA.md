# معماری SubTube

این سند توضیح می‌دهد SubTube چطور کار می‌کند؛ ساده و قدم‌به‌قدم، بر اساس سورس واقعی (`src/index.js`).

## تصویر کلی

```
کاربر در تلگرام لینک یوتیوب می‌فرستد
        │
        ▼
Telegram Bot API ──(Webhook)──► Cloudflare Worker (subtube-bot)
                                        │
                     پاسخ فوری + دکمه‌های انتخاب حالت
                                        │
                                        ▼
                              Cloudflare Queue (subtube-jobs)
                                        │
                                        ▼
                 پردازش در مصرف‌کننده صف (سقف ۱۵ دقیقه):
                 ۱) استخراج زیرنویس  ۲) ترجمه به فارسی
                 ۳) ساخت SRT  ۴) خلاصه (اختیاری)  ۵) تحویل
                                        │
        ┌───────────────┬───────────────┼────────────────┐
        ▼               ▼               ▼                ▼
   D1 (کاربران،    KV (کش ترجمه،   Supadata و       Coarena / Gemini /
   پردازش‌ها،       پیشرفت زنده،    مسیرهای         Google Translate
   آمار، تنظیمات)   فایل آماده)     استخراج یوتیوب   (موتورهای ترجمه)
```

## چرا صف (Queue)؟

اندازه‌گیری واقعی این پروژه نشان داد اجرای پس‌زمینه پشت وبهوک تلگرام حدود ۳۰ ثانیه
بعد از پاسخ قطع می‌شود و پردازش‌های طولانی بی‌صدا می‌مردند. برای همین وبهوک فقط
درخواست را داخل صف می‌گذارد و مصرف‌کننده صف — با سقف ۱۵ دقیقه — کار اصلی را انجام می‌دهد.

## بخش‌های سورس

سورس یک فایل باندل‌شده است؛ بخش‌ها با `// src/...` مشخص شده‌اند:

| بخش | وظیفه |
|---|---|
| `src/utils/validation.js` | تشخیص لینک یوتیوب و استخراج شناسه ویدیو؛ حداکثر ۳ لینک یکتا در هر پیام |
| `src/telegram/webhook.js` | بررسی سکرت وبهوک (مقایسه ثابت‌زمانی) و کلاینت تلگرام (`sendMessage`، ارسال سند، ویرایش پیام و…) |
| `src/telegram/messages.js` | همه متن‌های فارسی ربات (خوش‌آمد، راهنما، خطاها، آمار) |
| `src/utils/errors.js` | پاک‌سازی پیام خطا تا جزئیات داخلی سرویس‌ها به کاربر نشت نکند |
| `src/database/users.js` | ثبت/به‌روزرسانی کاربر و خواندن تنظیمات از جدول `settings` |
| `src/database/jobs.js` | چرخه عمر پردازش: ساخت اتمیک، تکمیل، خطا، پاک‌سازی پردازش‌های کهنه (۱۰ دقیقه) |
| `src/database/stats.js` | آمار هر کاربر از `user_stats` و `users` |
| `src/youtube/parser.js` | تجزیه فرمت‌های زیرنویس VTT و JSON3 و XML، تمیزکردن متن و نرمال‌سازی زمان‌بندی |
| `src/youtube/extractor.js` | استخراج زیرنویس با چند مسیر (بخش بعد) |
| `src/translator/google-translate.js` | هر سه موتور ترجمه + خلاصه‌ساز + سهمیه Coarena (نام تاریخی فایل در باندل) |
| `src/subtitle/srt-generator.js` | شکستن متن به حداکثر ۲ خط ۴۲کاراکتری و ساخت SRT |
| `src/telegram/handlers.js` | مغز ربات: دستورات، دکمه‌های انتخاب، پیشرفت زنده، تحویل فایل، صف |
| `src/index.js` | نقطه ورود: مسیرهای HTTP و مصرف‌کننده صف |

## مسیرهای HTTP

| مسیر | توضیح |
|---|---|
| `GET /` و `GET /health` | سلامت سرویس؛ پاسخ JSON ساده |
| `POST /webhook` | دریافت آپدیت‌های تلگرام (با بررسی سکرت) |
| `GET /f/<token>` | دانلود فایل SRT آماده از KV (اعتبار ۴۸ ساعت) |
| `GET /p/<token>` | صفحه وب پیشرفت زنده یک پردازش؛ `/p/<token>/json` نسخه JSON برای پولینگ |
| `GET /_diag` | عیب‌یابی داخلی؛ فقط با `DIAG_TOKEN` (استخراج آزمایشی، مدل‌ها، وبهوک، دستورات) |

## استخراج زیرنویس چطور کار می‌کند؟

مدیر استخراج (`extractEnglishSubtitles`) مسیرها را به ترتیب امتحان می‌کند و اولین
نتیجه قابل‌قبول را برمی‌گرداند:

1. **Supadata** (مسیر اصلی) — API رسمی استخراج ترنسکریپت؛ سریع و پایدار از دیتاسنتر کلادفلر.
2. **صفحه تماشای یوتیوب (Watch Page)** — خواندن داده پخش‌کننده از HTML صفحه.
3. **Innertube** — API داخلی پخش‌کننده یوتیوب با کلاینت‌های ANDROID / iOS / WEB_EMBEDDED.
4. **Timedtext** — اندپوینت رسمی فهرست زیرنویس‌های یوتیوب.
5. **Invidious** — چند نمونه عمومی Invidious به‌صورت موازی.

چرا این‌همه مسیر؟ چون یوتیوب برای درخواست‌های مستقیم از IP دیتاسنترها معمولاً
دیوار ربات می‌گذارد؛ تنوع مسیر یعنی شانس موفقیت بالاتر. اگر زبان مبدأ انگلیسی
نباشد، استخراج بدون قید زبان دوباره تلاش می‌شود و زبان واقعی تشخیص داده می‌شود.
اگر خود ویدیو زیرنویس فارسی آماده داشته باشد، همان بدون ترجمه تحویل می‌شود و
به کاربر اطلاع داده می‌شود.

زیرنویس خام بعد از استخراج **نرمال** می‌شود: مرتب‌سازی زمانی، ادغام خط‌های
هم‌پوشان، سقف ۷ ثانیه برای هر خط و حذف تکراری‌ها (`normalizeCues`).

## ترجمه چطور کار می‌کند؟

1. خط‌ها به تکه‌های (Chunk) مناسب تقسیم می‌شوند (`buildTranslationChunks`).
2. هر خط یک **شناسه سراسری** دارد؛ مدل باید پاسخ را با همان شناسه برگرداند
   (`{id, fa}`). تکه‌ای که مجموعه شناسه‌هایش دقیقاً با ورودی نخواند، رد و دوباره تلاش می‌شود.
   این طراحی جلوی فاجعه «ترجمه‌ها یک خط جابه‌جا شوند» را می‌گیرد.
3. ترتیب موتورها: **Coarena** (پیش‌فرض؛ با استخر دو کلید و تعویض خودکار هنگام
   اتمام سهمیه یا خطای احراز) ← **Gemini** ← **Google Translate** (مسیر پشتیبان هر تکه).
   ارائه‌دهنده و مدل از جدول `settings` دیتابیس خوانده می‌شوند و بدون Deploy قابل تغییرند.
4. در پایان، `validateTranslatedCues` تعداد و زمان‌بندی را با اصل مقایسه می‌کند؛
   اگر نخواند، فایل خراب تحویل داده نمی‌شود و پردازش خطا می‌خورد.
5. نتیجه موفق در KV **کش** می‌شود (۴۸ ساعت)؛ درخواست تکراری همان ویدیو فوری جواب می‌گیرد.

## پیشرفت زنده

برای هر پردازش یک وضعیت مرحله‌ای نگه داشته می‌شود (استخراج، ترجمه با شمارش خط‌به‌خط،
ساخت فایل، تحویل). پیام وضعیت تلگرام حدود هر ۲٫۵ ثانیه ویرایش می‌شود و فقط عنوان،
نوار و درصد را نشان می‌دهد. نسخه کامل در صفحه `/p/<token>` است. اگر وضعیت بیش از
۱۵۰ ثانیه بی‌حرکت بماند، «متوقف‌شده» حساب می‌شود و پردازش‌های کهنه بعد از ۱۰ دقیقه
به‌صورت خودکار ناموفق بسته می‌شوند.

## تحویل فایل

تحویل یک نردبان سه‌پله‌ای است (`deliverSrt`)، چون ورودی رسانه تلگرام از سمت
Workers گاهی معطل می‌شود:

1. لینک دانلود `/f/<token>`
2. آپلود مستقیم فایل (با پروب ۱۵ ثانیه‌ای)
3. ارسال متن زیرنویس در تکه‌های حداکثر ۳۵۰۰ کاراکتری

## محدودیت‌ها و محافظ‌ها

- سقف پردازش هم‌زمان تکراری برای یک ویدیو + سقف ساعتی هر کاربر (پیش‌فرض ۱۰).
- سقف حجم ویدیو: `MAX_CUE_COUNT` (پیش‌فرض ۱۲۰۰ خط) و `MAX_TOTAL_CHARS` (پیش‌فرض ۴۵۰۰۰ کاراکتر).
- لغو با `/cancel`: یک پرچم در KV (اعتبار ۱ ساعت) که در چند نقطه پردازش بررسی می‌شود.
- خاموش‌کردن فوری ربات با تنظیم `bot_enabled=false` در دیتابیس، بدون Deploy.

## Cron Job

**وجود ندارد.** SubTube هیچ زمان‌بندی (Cron Trigger) ندارد؛ همه‌چیز رویدادمحور است:
وبهوک تلگرام، صف، و درخواست‌های HTTP.
